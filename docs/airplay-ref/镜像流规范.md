## 1. Wire format of the mirroring stream

Transport: a single **TCP** connection, receiver = server.
`raop_rtp_mirror_init_socket()` (`raop_rtp_mirror.c:862-890`):
`netutils_init_socket(&dport, use_ipv6, 0)` → third arg `use_udp==0` → `SOCK_STREAM`
(`netutils.c:114-130`), then `listen(dsock, 1)` (`:874`). The **client** connects;
the receiver `accept()`s one connection (`:239-252`).

Framing: a repeating sequence of

```
+------------------------ 128-byte header ------------------------+  +--- payload ---+
| 0..3  | 4..7      | 8..15        | 16..127                     |  | payload_size   |
| size  | type+opt  | timestamp    | type-specific               |  | bytes          |
+---------------------------------------------------------------+  +----------------+
```

There is **no length field covering the header**, no packet delimiter, no sequence
number and **no SSRC field anywhere in the mirroring protocol** (grep for `ssrc` over
`lib/**`: zero hits). Do not expect an RTP header: the standard RTP fields
(seqnum/SSRC) exist only in the *audio* stream (`raop_rtp.c:557-565`).

Header is always read as exactly **128 bytes**, unconditionally, for every packet:
`raop_rtp_mirror.c:297-303` — comment `:297`
`// The first 128 bytes are some kind of header for the payload that follows`,
loop `while (payload == NULL && readstart < 128)` with `recv(..., 128 - readstart, 0)`.
Read it with a "read exactly N bytes" loop (multiple TCP segments are expected; the
code loops for that reason).

### Header fields

| Offset | Size | Field | How UxPlay reads it |
|---|---|---|---|
| 0..3 | 4 | `payload_size` — number of payload bytes that follow the 128-byte header | `byteutils_get_int(packet, 0)` = **little-endian** u32 (`raop_rtp_mirror.c:321`, `byteutils.c:61-63`; file comment `byteutils.c:49`: "The functions in this file assume a little endian cpu architecture!") |
| 4 | 1 | payload **type** (`packet[4]`) | plain byte, `switch (packet[4])` at `:389` |
| 5 | 1 | sub-type / flag (`packet[5]`) | documented at `:339-344`: `0x00` = non-IDR VCL NAL, `0x10` = IDR VCL NAL; never branched on in code |
| 6 | 1 | option low byte (`packet[6]`) | `:346-352`, `:580-586` |
| 7 | 1 | option high byte (`packet[7]`) | `0x01` for the observed codec packets, `0x00` for old protocol; never branched on |
| 8..15 | 8 | timestamp | `byteutils_get_long(packet, 8)` = **little-endian** u64, treated as Q32.32 (`seconds = v>>32`, `fraction = v & 0xffffffff`) — `raop_rtp_mirror.c:331-332`, `raop_ntp.c:955-960` |
| 16..127 | 112 | type-specific; zero for `0x00`/`0x02`; **width/height floats for `0x01`** (§5); unused for `0x05` | `:560-572`, `:594-602` |

The 4 header bytes 4..7 are also logged as hex (`:322-329`) — logging only.

Notes on the timestamp:
* It is the client's own wall clock; UxPlay's comment (`:393-397`) says it does **not**
  include `SECONDS_FROM_1900_TO_1970` — "it's really just counting nano seconds since
  last boot" (Q32.32 fixed point, seconds in the high half).
* The absolute epoch is unimportant: UxPlay calls
  `raop_ntp_adjust_remote_timestamp_offset(ntp, raw, true)` (`:331`), which on the first
  call establishes `fixed_offset = local_ref_time - (raw + 2208988800<<32)` and
  thereafter returns `raw + 2208988800<<32 + fixed_offset`
  (`raop_ntp.c:1011-1036`, constant literal `2208988800ULL` at `:1014`;
  `SECONDS_FROM_1900_TO_1970 2208988800ULL` in `byteutils.h:27`;
  `raop_ntp.c:51 #define RAOP_NTP_CLOCK_BASE (2208988800ull << 32)` is defined but **unused**).
* Only **monotonic relative** timestamps matter for video. If your client's timestamps do
  not increase ~linearly with arrival time when read little-endian, byte-swap them.
* `packet[8:15]` is meaningless for type `0x05` (`:363`, `:787`). UxPlay nevertheless
  computes it before the switch and uses the *first packet of any type* to establish
  `video_arrival_offset` (`:333-337`) — for a re-implementation, derive the offset from
  the first **type-0x00** packet instead.

### "Old protocol" vs current

There is **no branch on a protocol version field** anywhere. The old protocol is
detected from the RTSP `User-Agent` and manifests in three places:

1. `raop_handlers.h:815-822` — `old_protocol = true` if `strstr(OLD_PROTOCOL_CLIENT_USER_AGENT_LIST, user_agent)`
   or `strstr(user_agent, "AirMyPC")`;
   `global.h:26 #define OLD_PROTOCOL_CLIENT_USER_AGENT_LIST "AirMyPC/2.0;xxx"`.
2. Effect (`raop_handlers.h:824-861`): for old-protocol clients the FairPlay-decrypted
   16-byte `aeskey` is **not** hashed with the pairing ECDH secret before being handed to
   `raop_rtp_mirror_init()`; for normal clients `aeskey = SHA512(aeskey||ecdh_secret)[0:16]`.
   This changes the video key/IV derived in §4.
3. On the wire, old protocol shows up as a once-per-second header-only packet with
   `packet[4]=0x02`, `packet[5]=0x00`, `packet[6]=0x1e`, `packet[7]=0x00`, `payload_size = 0`
   (`:343`, `:348`, `:779-783`). No other header-layout difference exists in this source:
   the header is 128 bytes in all cases. (A "128-byte header" is also stated in
   `lib/raop_rtp_mirror.c` for both codecs.)

## 3. Extracting H.264 from a `0x00` packet

Steps exactly as in `raop_rtp_mirror.c`:

1. Read 128-byte header (§1).
2. `payload_size = LE32(header[0..3])`; read **exactly** `payload_size` bytes into a
   separate buffer (`:365-376`). The payload does **not** include the 128-byte header.
3. Decrypt those `payload_size` bytes in place/into an output buffer (§4) —
   `mirror_buffer_decrypt(buffer, payload, payload_decrypted, payload_size)` (`:451`).
   AES-CTR is length-preserving (`:450` comment).
4. The plaintext is a sequence of **AVCC-style NAL units: `[BE32 nalu_length][nalu bytes]`**
   repeated until the payload is exhausted (`:453-458`). The 4-byte length prefixes *are*
   part of the encrypted region. There can be more than one NAL per packet: e.g. on M1/M2
   Macs an SEI (type 6) NAL is prepended in front of the IDR (`:354-359`, `:417-421`).
5. Rewrite each 4-byte length prefix **in place** with the Annex-B start code
   `00 00 00 01` (`nal_start_code` declared `:192`; `memcpy(payload_decrypted + nalu_size, nal_start_code, 4)` `:467`),
   then advance by `4 + nalu_length` (`:468`, `:530`).
   This is the exact byte sequence the decoder must be handed: **Annex-B, 4-byte start
   codes, no length prefixes, no emulation-prevention insertion.**
6. Validation (used as a decryption-success heuristic) — `:458-474`, `:532`:
   * `nc_len = BE32(payload_decrypted + nalu_size)`;
     reject if `nc_len < 0` **or** `nalu_size + 4 > payload_size` **or**
     `nc_len > payload_size - nalu_size - 4`;
   * first byte of each NAL must have `forbidden_zero_bit == 0`
     (`if (payload_decrypted[nalu_size] & 0x80) invalid`);
   * at the end `nalu_size` must equal `payload_size` exactly.
   On failure: `payload_out[0] = 1;` "mark video data as invalid h264 (failed decryption)"
   (`:533-536`) and the buffer is still delivered.
7. NAL-type sanity switch (h264): type `1` (non-IDR slice), `5` (IDR slice), `6` (SEI),
   `7` (SPS), `8` (PPS), `14` (prefix NAL, "seen before all VCL Nalu's in AirMyPc") are
   accepted; types `2/3/4` (partitioned slices) and anything else log a warning only
   (`:475-529`). `ref_idc = byte >> 5` (unused).
8. Deliver: `video_decode_struct { is_h265, nal_count, data, data_len, ntp_time_local,
   ntp_time_remote }` (`lib/stream.h:24-31`) via
   `callbacks.video_process(cls, ntp, &video_data)` (`:556`); the receiver frees the buffer.
   `data_len = payload_size` (+ `sps_pps_len` when SPS/PPS were prepended, `:547-554`).

SPS/PPS are **injected in-band by the receiver, not by the client**: an `0x01` packet's
SPS/PPS are stored and prepended (Annex-B) to the *next* `0x00` packet whose raw header
timestamp equals the `0x01` packet's raw timestamp (`:426-433` compare, `:435-445` prepend,
`:547-554` accounting). If the timestamps differ, the stored SPS/PPS are dropped (`:426-433`).
The SPS/PPS packet and the following IDR always carry the same timestamp (`:354-359`).
Net effect for the decoder: each access unit is `00 00 00 01 SPS 00 00 00 01 PPS 00 00 00 01 IDR…`.

## 4. Decryption of `0x00` payloads (AES-128-CTR, continuous keystream)

### Key and IV derivation (`mirror_buffer.c:40-92`)

Inputs: the 16-byte FairPlay-decrypted `aeskey` from RTSP ANNOUNCE (`RAOP_AESKEY_LEN 16`,
`raop_rtp.h:27`; obtained at `raop_handlers.h:795-807`, optionally hashed with the pairing
ECDH secret at `:824-861`) and the 64-bit `streamConnectionID` from the SETUP stream dict
(`raop_handlers.h:959-966`).

```c
unsigned char aeskey_video[64] = {0}, aesiv_video[64] = {0};
snprintf(aeskey_video, 64, "AirPlayStreamKey%" PRIu64, *streamConnectionID);   // :52
snprintf(aesiv_video,  64, "AirPlayStreamIV%"  PRIu64, *streamConnectionID);   // :53
sha_ctx_t *ctx = sha_init();                       // SHA-512  (crypto.c:511 EVP_sha512)
sha_update(ctx, aeskey_video, strlen(aeskey_video));
sha_update(ctx, mirror_buffer->aeskey_audio, RAOP_AESKEY_LEN);   // the 16 audio aeskey
sha_final(ctx, aeskey_video, NULL);                // 64-byte digest written in place
sha_reset(ctx);
sha_update(ctx, aesiv_video, strlen(aesiv_video));
sha_update(ctx, mirror_buffer->aeskey_audio, RAOP_AESKEY_LEN);
sha_final(ctx, aesiv_video, NULL);
aes_ctx = aes_ctr_init(aeskey_video, aesiv_video); // uses first 16 bytes of each digest
```

So: `AESKey = SHA512("AirPlayStreamKey" + decimal(streamConnectionID) ‖ audioAESKey)[0..15]`,
`AESIV = SHA512("AirPlayStreamIV" + decimal(streamConnectionID) ‖ audioAESKey)[0..15]`.
Note it is **SHA-512** even though the log text at `raop_handlers.h:857` says "sha-256";
`sha_init()` is hard-wired to `EVP_sha512()` (`crypto.c:505-515`).
`aes_ctr_init` = `EVP_aes_128_ctr()` with the 16-byte IV as the initial **counter block**
(`crypto.c:141-143`).

`mirror_buffer_init_aes()` is called from the SETUP handler when a type-110 stream is set
up (`raop_handlers.h:965-967`), and it **resets stream state**
(`mirror_buffer.c:66-74`: `nextDecryptCount = 0`, `memset(og,0,16)`, destroy+recreate the
CTR context) — "A re-key means a new stream, so the keystream restarts". A new SETUP for
type 110 therefore restarts the keystream at the original IV.

### Which bytes are encrypted

Only the **payload** of type-`0x00` packets (payload bytes = `payload_size`, i.e. bytes
`128 .. 128+payload_size-1` of the packet), starting at payload offset 0. The 128-byte
header is never encrypted and is never fed to the cipher; `0x01`/`0x02`/`0x05` payloads are
not encrypted and do not advance the keystream.

### The exact algorithm (`mirror_buffer.c:94-124`, called from `raop_rtp_mirror.c:451`)

```c
void mirror_buffer_decrypt(mirror_buffer_t *mb, unsigned char *input, unsigned char *output, int inputLen) {
    if (mb->nextDecryptCount > 0)                                     // :96
        for (i < mb->nextDecryptCount) output[i] = input[i] ^ mb->og[16 - mb->nextDecryptCount + i]; // :97-99
    int encryptlen = ((inputLen - mb->nextDecryptCount) / 16) * 16;   // :102
    aes_ctr_start_fresh_block(mb->aes_ctx);                           // :104
    aes_ctr_decrypt(mb->aes_ctx, input + mb->nextDecryptCount, input + mb->nextDecryptCount, encryptlen); // :105-106
    memcpy(output + mb->nextDecryptCount, input + mb->nextDecryptCount, encryptlen);  // :108
    int restlen  = (inputLen - mb->nextDecryptCount) % 16;            // :111
    int reststart = inputLen - restlen;                               // :112
    mb->nextDecryptCount = 0;                                         // :113
    if (restlen > 0) {
        memset(mb->og, 0, 16); memcpy(mb->og, input + reststart, restlen);  // :115-116
        aes_ctr_decrypt(mb->aes_ctx, mb->og, mb->og, 16);                   // :117  (16 bytes!)
        for (j < restlen) output[reststart + j] = mb->og[j];                // :118-120
        mb->nextDecryptCount = 16 - restlen;                                // :122
    }
}
```

Semantics, precisely:

* **Not CBC.** No IV per packet, no chaining, no reset per packet, nothing is derived from
  the header, and the 16-byte "header block"/first bytes of the ciphertext have **no special
  role** — the ciphertext starts at payload offset 0 and the keystream is simply XORed over
  it. (`aes_cbc_decrypt(&data[12], …)` + `aes_cbc_reset()`, i.e. "12-byte header skipped,
  whole-block CBC, tail in clear, IV re-set every packet", is `raop_buffer.c:130-137`, the
  **audio** path — do not apply it to video.)
* Each call consumes exactly `inputLen` keystream bytes for the payload, plus up to 15 bytes
  of the following keystream block which are held in `og` and applied to the **first bytes
  of the next payload**. Invariant after each call:
  `keystream_position == total_payload_bytes_so_far + nextDecryptCount`.
  ⇒ **The AES-CTR keystream is one single continuous stream across all successive
  type-`0x00` payloads of the session** (it is *not* restarted per packet; only a new
  `streamConnectionID`/new SETUP restarts it).
  A from-scratch implementation can therefore ignore `og`/`nextDecryptCount` entirely and
  keep one CTR keystream: for each `0x00` packet, XOR ciphertext[j] with keystream[j]
  continuing where the previous packet stopped. `SPS/PPS`/`0x05`/`0x02` payloads are skipped.
* `aes_ctr_start_fresh_block()` (`crypto.c:150-154`) only advances the OpenSSL CTR stream to
  the next block boundary when `ctx->block_offset != 0`, by encrypting the throwaway global
  `waste` buffer (`crypto.c:48`) for `16 - block_offset` bytes. `block_offset` is only
  updated by `aes_ctr_encrypt()` (`crypto.c:145-148`), **never** by `aes_ctr_decrypt()`
  (`crypto.c:156-158`, which is just `aes_encrypt()`), and the CTR context is freshly created
  in `aes_ctr_init()` (`block_offset = 0`, `crypto.c:65`) — so in the mirroring path
  `aes_ctr_start_fresh_block()` is a **no-op** and OpenSSL's internal CTR offset is exactly
  the continuous-stream position above.
* Counter increment convention (needed if you implement CTR yourself, e.g. in .NET, since
  .NET has no built-in CTR): OpenSSL `EVP_aes_128_ctr` treats the 16-byte counter block as a
  **big-endian 128-bit integer incremented by 1 per block**; the initial block is the 16-byte
  IV, i.e. first keystream block = `AES-ECB-Encrypt(IV)`. Bytes of the payload are consumed
  in order; the byte at index `j` is XORed with keystream byte `j` (block `j/16`, byte
  `j%16`); the offset continues across packets.
* Padding is disabled everywhere (`crypto.c:80 EVP_CIPHER_CTX_set_padding(ctx, 0)`), and CTR
  has no padding, so payload sizes need not be multiples of 16 (typical VCL payloads are not).

## 5. The codec/params packet (`packet[4] == 0x01`)

Not encrypted (`:574-575`); it is parsed directly from the raw payload buffer. It always has
`payload_size > 0`; `payload_size == 0` means non-h264 video was sent while AirPlay features
bit 42 (`SupportsScreenMultiCodec`) was not advertised — UxPlay prints exactly that and
aborts the stream (`:615-621`).

### Header (128 bytes) — the layout UxPlay documents at `:560-572`, read at `:595-602`

```
bytes 0-15 : length + timestamp (as for all packets)
bytes 16-19: float width_source        (value is x.0000, x = unsigned short)   :595
bytes 20-23: float height_source                                               :596
bytes 24-39: all 0x0
bytes 40-43: float width_source   (duplication of width_0)                     :597
bytes 44-47: float height_source  (duplication of height_0)                    :598
bytes 48-51: float "other_w" (unidentified)                                    :599
bytes 52-55: float "other_h" (unidentified)                                    :600
bytes 56-59: float width                                                       :601
bytes 60-63: float height                                                      :602
bytes 64-127: all 0x0
```
(`byteutils_get_float` = little-endian IEEE-754 float, `byteutils.c:102-104`.)
These are the client's declared source/encoded dimensions; they are only informational
(`video_report_size` callback, `:609-613`). Note the comment block itself contains a
copy/paste error: it labels both 48-51 and 52-55 as `48-51`; the code reads 48 and 52.

### H.264 payload layout (`:709-762`)

```
payload[0..5]      : 6-byte config header (opaque; see below)
payload[6..7]      : SPS size, BIG-ENDIAN uint16            sps_size = get_short_be(payload, 6)
payload[8 .. 8+sps_size)                : SPS NAL (no start code)
payload[sps_size+8]                     : number_of_pps (1 byte, unused)
payload[sps_size+9 .. sps_size+11)      : PPS size, BIG-ENDIAN uint16
payload[sps_size+11 .. +pps_size)       : PPS NAL (no start code)
... remainder (>0 is ignored/logged: data_size = payload_size - sps_size - pps_size - 11)
```
Exact code: `sps_size = byteutils_get_short_be(payload,6)` `:725`;
`sps = payload + 8` `:726`;
`pps_size = byteutils_get_short_be(payload, sps_size + 9)` `:727`;
`pps = payload + sps_size + 11` `:728`.
The commented-out `h264codec_t` (`:65-77`) and the dead assignments (`:764-777`) name the
6-byte header as `version, profile_high, compatibility, level, reserved_6_and_nal,
reserved_3_and_sps` — i.e. a 6-byte AVCDecoderConfigurationRecord-like prefix; **UxPlay
never uses those bytes**, so the only reliable facts are the offsets above.

### HEVC detection and layout (`:626-708`, only relevant if you advertise bit 42)

Detected by `memcmp(payload + 4, "hvc1", 4)` with
`unsigned char hvc1[] = { 0x68, 0x76, 0x63, 0x31 };` (`:627-629`). Then, starting at
`payload + 0x75` (117) and advancing:
`{0xa0,0x00,0x01}` VPS tag, `{0xa1,0x00,0x01}` SPS tag, `{0xa2,0x00,0x01}` PPS tag
(`:646-648`); each is followed by a **big-endian uint16 size at tag+3** and the NAL data at
**tag+5** (`vps_size = byteutils_get_short_be(ptr, 3); ptr += 5;` `:657-659`, same for SPS
`:671-673`, PPS `:685-687`; the 4-byte `memcmp` therefore also requires the size's high
byte to be 0). The `hvc1` magic sits at `payload+4`, the tags at `payload+0x75`; bytes
between are ignored.

### What the receiver must do with it

* Build an Annex-B config buffer and hold it (`:754-762` h264, `:694-708` hevc):
  h264 → `sps_pps_len = sps_size + pps_size + 8`, contents
  `00 00 00 01 SPS 00 00 00 01 PPS`.
  hevc → `sps_pps_len = vps_size + sps_size + pps_size + 12`, contents
  `00 00 00 01 VPS 00 00 00 01 SPS 00 00 00 01 PPS`.
* Set `prepend_sps_pps = true` (`:763`) and remember the packet's raw timestamp
  (`ntp_timestamp_nal = ntp_timestamp_raw`, `:592`).
* On the next `0x00` packet: if the raw timestamps differ, **discard** the stored config;
  if equal, prepend it to that packet's output and clear the flag (`:426-445`, `:547-554`).
  `nal_count` is incremented by 2 (h264) or 3 (hevc) when prepending.
* A codec **change** after the first SPS/PPS is a fatal protocol error in UxPlay
  (`conn_reset`, `:631-645`, `:710-724`); the codec is latched from the first config packet
  (`video_set_codec`, `raop.h:68-70 VIDEO_CODEC_UNKNOWN/H264/H265`).
* The `0x01` packet's `packet[6]` also drives suspend/resume of decoding
  (`0x56`/`0x5e` ⇒ `video_pause()`, `0x16`/`0x1e` while suspended ⇒ `video_resume()`,
  `:580-589`).

## 6. Timing / keepalive: what the receiver must send

**The mirroring TCP socket is strictly receive-only.** `raop_rtp_mirror.c` contains no
`send()`/`write()` on `stream_fd` or `mirror_data_sock` at all — only `accept` (`:246`),
`recv` (`:300`, `:373`), `setsockopt` (`:258-290`) and `close` (`:837`). There is **no RTCP,
no receiver report, no resend request, and no video feedback** in the mirroring path.

The only thing the receiver transmits for mirroring is the **NTP/timing exchange**:

* Setup: `raop_ntp_init(...remote, remotelen, timing_rport, &time_protocol)` +
  `raop_ntp_start(conn->raop_ntp, &timing_lport)` at SETUP (`raop_handlers.h:897-925`);
  `timing_rport` comes from the client's SETUP plist key `timingPort` (`:897-907`),
  `timing_lport` is UxPlay's own UDP port, reported back in the SETUP reply as `timingPort`
  (`:934-935`).
* The receiver **initiates**: it sends a 32-byte timing request from its own socket to the
  client's timing port and waits for the reply (`raop_ntp.c:575-576` fixed request bytes
  `{0x80,0xd2,0x00,0x07,0x00,…}`; `byteutils_put_ntp_timestamp(request, 24, send_time)`
  `:611`; `sendto(...)` `:612-613`; response parsed at offsets 8/16/24 big-endian `:651-662`).
  This is classic NTP 4-timestamp offset computation (`t1..t4`, `:736-748`); the
  "client_ref" is echoed back in request bytes 8..15 (`:660`).
* Cadence: `NTP_BURST_LIMIT = RAOP_NTP_DATA_COUNT = 8` (`raop_ntp.c:43`, `:568`).
  While `ntpcount <= 8`: **every 0.25 s** (`wait_time.tv_nsec += 250000000`, `:837`);
  afterwards: **every 3 s** (`wait_time.tv_sec += 3`, `:835`); loop at `:831-845`.
* Required or optional? **Not required for video to keep flowing.** Nothing in the mirroring
  path waits on the timing state; frames are pushed as they arrive. What timing buys is
  PTS mapping. In this revision it is effectively not even used for video: all three
  converters bail out with `return 0` unless `raop_ntp->client_time_received` is true
  (`raop_ntp.c:975,988,1001`) and that flag is **only ever set to `false`** (init `:441`) —
  it is never set true anywhere in the tree. Consequently
  `raop_rtp_convert_remote_time()` returns 0, `video_decode_struct.ntp_time_local` is 0
  (`raop_rtp_mirror.c:398`), and the application substitutes the packet arrival time
  (`uxplay.cpp:2737-2739`):
  ```c
  if (!remote_clock_offset) remote_clock_offset = (data->ntp_time_local ? data->ntp_time_local : get_local_time()) - data->ntp_time_remote;
  data->ntp_time_remote += remote_clock_offset;   // PTS handed to the renderer
  ```
  i.e. **the usable clock mapping for video is: offset = local_arrival_time(first packet) −
  raw_timestamp(first packet), PTS = raw_timestamp + offset** (with the renderer correcting
  drift up to 10 times, `uxplay.cpp:2741-2751`). So for a minimum viable receiver you can
  implement §1/§3/§4 and ignore NTP entirely; implement the timing thread only if you want
  A/V-sync-accurate audio alongside mirroring.
* Whether a *given* client stops sending video if the receiver never answers/sends timing
  packets cannot be determined from this source (UxPlay always runs the thread whenever the
  client's SETUP carried `ekey`/`eiv`). Note `raop_ntp.c` only ever *sends* requests and
  parses responses; UxPlay's timing socket does not implement an NTP server for a client that
  probes it.

Other client→receiver requests the receiver must answer during a session (RTSP, `raop.c:406-444`):
`OPTIONS` (`Public: SETUP, RECORD, FLUSH, TEARDOWN, OPTIONS, GET_PARAMETER, SET_PARAMETER`,
`raop_handlers.h:596`), `ANNOUNCE`, `SETUP`, `RECORD` (replies `Audio-Latency` and
`Audio-Jack-Status: connected; type=analog`, `:1227-1228`), `GET_PARAMETER`,
`SET_PARAMETER` (including `progress:` which UxPlay only forwards to the local app,
`raop_handlers.h:1156-1159` → `raop_rtp.c:813-822`; **the receiver never sends
`SET_PARAMETER progress` to the client**), `POST /feedback` (client heartbeat; the handler
just records it, `raop_handlers.h:1206-1215`); the generic reply adds
`Server: AirTunes/<GLOBAL_VERSION>` and echoes `CSeq` (`raop.c:488-493`,
`global.h:22 GLOBAL_VERSION "220.68"`), so **echo `CSeq` in every RTSP response** or the
client will desynchronise its request pipeline.

There is no RTSP-level keepalive the receiver must emit; the client drives everything.

## 7. Stream setup (RTSP `SETUP`, stream type 110)

Handler: `raop_handler_setup` (`raop_handlers.h:599-1067`). Request body is a binary plist
(`Content-Type: application/x-apple-binary-plist`); it is parsed with `plist_from_bin`
(`:626`). Two SETUP requests occur in practice: an initial one carrying `ekey`/`eiv`, and a
following one carrying `streams` (the code handles both in one handler, `:633` guard).

### Values the receiver learns

| Key | Where read | Use |
|---|---|---|
| `ekey` (72-byte data) | `:627`, `:795-799` | FairPlay-decrypt → 16-byte `aeskey` (`:807`) — input to the video key/IV hash (§4) and the audio key |
| `eiv` (16-byte data) | `:628`, `:785-786` | 16-byte audio AES-CBC IV (logged at `:791` as "needed for AES-CBC audio decryption iv"); **not** used for video |
| `timingProtocol` (string) | `:873-896` | must be `"NTP"`; "None"/other ⇒ error logged. If absent ⇒ `TP_UNSPECIFIED` and "old protocol without offset will be used" (`:892-896`) |
| `timingPort` (uint) | `:897-907` | client's UDP timing port (destination of the receiver's timing requests). If 0, error: "may be using unsupported AirPlay2 Remote Control protocol" |
| `isRemoteControlOnly` (bool) | `:864-872` | if true, error: AirPlay2 Remote-Control protocol is not supported |
| `deviceID`, `model`, `name` | `:644-646`, `:756-759` | identification / admission |
| `streams` (array of dicts) | `:942-1058` | one entry per stream |
| ↳ `type` (uint) | `:949-951` | `110` = mirroring, `96` = audio; anything else ⇒ error + disconnect (`:1053-1056`) |
| ↳ `streamConnectionID` (uint64) — **type 110 only** | `:959-963` | input to the video key/IV SHA-512 (§4) |
| ↳ `controlPort` (uint) — type 96 only | `:991-993` | "must != 0 to activate audio resend requests" |
| ↳ `ct`, `spf`, `audioFormat`, `isMedia`, `usingScreen` — type 96 only | `:995-1030` | audio codec params |

**`latency` is not read anywhere.** A case-insensitive search for `latenc` over all
`*.c/*.h/*.cpp` finds only: the audio `Audio-Latency` response header (`raop_handlers.h:1223-1227`),
the `audioLatencies` array in the `/info` response (`:171-193`), and log strings. There is no
`latency` plist key parsed out of SETUP (or ANNOUNCE). Do not wait for one; a conforming
receiver may ignore it.
`dataPort` / `eventPort` are **not** read from the request for type 110 — the receiver
*chooses* the mirroring data port itself and only reports it.

### What the receiver must reply (type 110)

Response body is a binary plist (`plist_to_bin`, `:1063`; header
`Content-Type: application/x-apple-binary-plist`, `:1066`):

```
{
  "timingPort": <uint16, receiver's UDP timing port>,        // :934-935
  "eventPort" : 0,                                           // :931-936  ("the event port is not
                                                             //            used in mirror mode or audio mode")
  "streams"   : [ { "type": 110, "dataPort": <uint16> } ]     // :974-979
}
```
For type 96 the stream dict additionally contains `"controlPort"` (`:1041-1048`).
Nothing else in the reply is required to start mirroring (the `/info` plist with
`displays`/`width`/`height`/`refreshRate`/`maxFPS`/`overscanned` governs the resolution the
client chooses, `raop_handlers.h:215-243`).

### Who connects to whom

* **Mirroring video: the sender connects to the receiver.** The receiver picks
  `dport = raop->mirror_data_lport` (`:958`; from `raop_set_tcp_ports()` /
  `raop_set_udp_ports()`, `raop.c:781-794`, default `tcp[0] = 7100` when `-p` is given with
  no value, `uxplay.cpp:1690-1694`; 0 means "dynamically assigned", `uxplay.cpp:3155`),
  binds and `listen()`s (`raop_rtp_mirror.c:868-876`), reports the port as `dataPort`
  (`:975-977`), and the client connects from an ephemeral port; the receiver
  `accept()`s (`:239-252`). It accepts **one** connection (`listen(dsock, 1)`), does not
  validate the peer address, sets `SO_RCVTIMEO = 5 ms` (`:255-263`), then
  `SO_KEEPALIVE` with `TCP_KEEPIDLE = 60 s`, `TCP_KEEPINTVL = 10 s`, `TCP_KEEPCNT = 6`
  (`:265-290`; on Windows these names default to `3/17/16` per `:37-47`).
  Mirroring starts *inside the SETUP handler* (`raop_rtp_mirror_start()` `:967`), before the
  client has even connected.
* **Timing (NTP): receiver → client.** Receiver sends UDP requests to the client's
  `timingPort` (§6); the client replies to the receiver's source port.
* **Audio (type 96): client → receiver.** Receiver binds UDP data/control ports and returns
  them (`raop_rtp.c:241-270`, `netutils_init_socket(..., use_udp=1)`); the client sends RTP
  audio to `dataPort`; the receiver sends resend requests to the client's `controlPort`
  (`raop_rtp.c:203-230`) — this is the only case where UxPlay sends feedback for media.
* The receiver never performs an RTSP request towards the client for type-110 mirroring.
  (Only the AirPlay-2/HLS video path acts as an HTTP client, which is a different mode.)

## 8. Implementation checklist (C#/.NET)

1. TCP listen on the port you will advertise as `dataPort` (e.g. 7100) when you answer
   SETUP `streams:[{type:110,streamConnectionID:N}]`; advertise it plus `timingPort`,
   `eventPort=0`.
2. Derive `AESKey`/`AESIV` per §4, using the *same* 16-byte FairPlay key you use for audio
   (and, if the client is not "AirMyPC"-style old protocol and pairing established an ECDH
   secret, the SHA-512-hashed variant of that key as UxPlay does).
3. Per connection: read exactly 128 bytes → `payload_size = BitConverter.ToUInt32(h,0)`
   (LE) → read exactly `payload_size` bytes → dispatch on `h[4]`; ignore/consume unknown
   types.
4. Type `0x00`: XOR the payload against a **single continuous AES-128-CTR keystream**
   (counter = IV, incremented as a big-endian 128-bit integer per 16-byte block, ECB-encrypt
   the counter to get keystream), then replace each BE32 length prefix with `00 00 00 01`;
   prepend the buffered config if the timestamp matches; hand the resulting Annex-B buffer to
   your H.264 (or HEVC) decoder.
5. Type `0x01`: parse SPS/PPS (or VPS/SPS/PPS) per §5, build the Annex-B config buffer and
   hold it for the next `0x00` with the same raw timestamp; use `h[6]&0x40`-style
   (`0x56`/`0x5e`) packets to pause decoding.
6. Type `0x02`: ignore. Type `0x05`: read and discard (optionally parse the bplist when
   `payload_size > 25000`, using only the first `payload_size-25000` bytes).
7. PTS: `offset = localTimeOfFirstVideoPacket − rawTimestampOfFirstVideoPacket`;
   `pts = rawTimestamp + offset`.
8. Optionally run the NTP timing client (§6) — 0.25 s ×8 then every 3 s — only for A/V sync;
   never send anything on the mirroring TCP socket.

## 9. Not determinable from this source

* Byte order of the 8-byte timestamp as *written by the client*: the code reads it
  little-endian (`byteutils_get_long`, `raop_rtp_mirror.c:331`) and never byte-swaps; there
  is no explicit statement of the sender's encoding in the source. Implement little-endian
  first (that is what makes the arithmetic work) and byte-swap if the values are not
  monotonic.
* Meaning of `packet[5]` bits other than the `0x10` IDR note, of `packet[7]` (only `0x00`/`0x01`
  are ever observed), and of the header bytes 16..127 for types `0x00`, `0x02`, `0x05`.
* Any packet type other than `0x00`, `0x01`, `0x02`, `0x05` (in particular there is **no**
  `0x06` handler in this source, and no `0x03`/`0x04`).
* What the ~25000-byte trailer on some `0x05` packets contains ("unidentified content …
  seems to be the same data each time it is sent", `:787-789`).
* Whether any client requires the timing exchange (or the `eventPort`/`feedback` replies) to
  keep video flowing. UxPlay's own video path does not depend on them.
