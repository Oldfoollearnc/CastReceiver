## 二、关键决定（都是查证过的，不是拍的）

### 多设备并排：为什么最后**没有**搬动画源（这一条推翻了上一版计划）
上一版计划是"谁被放大就把那一路的 MediaSource 搬到主宿主上"。动手前先做了实测
（`tools/ui-spike/move-spike/`，直接编译产品源码 + 用真实 H.264 帧喂进去 + PrintWindow 取像素）：

| 步骤 | 结果 |
| --- | --- |
| 首次挂到主宿主 | ✅ 出画（1020/1023 采样点为亮） |
| `Detach(disposeSource:false)` 后挂到第二个宿主 | ❌ **3 秒后仍全黑**（状态停在 Buffering，`bright=0/1023`） |
| 再搬回原宿主 | ✅ 又出画（说明是"重开管道"的代价，不是宿主坏了） |
| 后创建的宿主先可见、下一轮布局再挂画面 | ✅ 出画（这条顺序是对的，并排新增一路就用它） |

结论：**MediaSource 确实能不被释放地搬动，但重开一次管道就要黑一段时间**，而"点一下换一路放大"
是个高频操作，不能接受。最终改成：

- **每一路各有一个自己的宿主**（`MultiViewTile`），每路的 MediaSource 从头到尾只挂在自己的宿主上，**一次都不搬**；
- 聚焦那一路的格子**留在同一个父容器里**，只改 Grid 的行列与尺寸（换父节点会销毁重建 HwndHost 子窗口，
  画面就得重挂 —— 小窗那次"一片黑"就是这么来的）；
- 主画面 = 当前聚焦那一路的宿主（`PrimaryHost`），所以截屏/录制/反截屏/小窗/状态浮层/画质档位
  **自动跟着聚焦那一路走**，不需要另写一套。

顺带解决了一件事：**每一路都必须喂帧**。早先所有会话共用一块 `MediaPlayer`，只能推聚焦那一路；
现在每路各有自己的解码器，不推的那几路格子就是全黑的。代价是 N 路 = N 个解码器（1080p30 下可接受），
换来的是"并排真的都在动"。

### 启动入场动画：最终形态（原生窗口 · WPF 之前就起播）
用户对前两版都不满意（"加了不如不加"、"不要小窗"、"为什么加底下那些进度条"、"要有音乐"、
"点开之后要黑等一会儿才出画面"）。第三版按这些要求重做：

| 要求 | 做法 |
| --- | --- |
| 点开就播、不要黑等 | 入场动画在 `Program.Main` 里**创建 WPF 之前**就起播：原生 Win32 窗口 + `Windows.UI.Composition`（`Compositor` + `DesktopWindowTarget` + `MediaPlayer.GetSurface` 的 SurfaceBrush），完全不经过 WPF。WPF 那 1.6 秒固定开销（解析 XAML ~700ms + 显示第一个窗口 ~950ms）被这块画面盖住 |
| 不要小窗 / 不要另一个界面 | 原来 360×180 的转圈小窗整块删掉；入场窗口就用**主窗口的位置与大小**（读上次关闭时保存的窗口矩形），交接严丝合缝，看起来就是主界面上盖了一层 |
| 不要进度条/文字 | 只有画面，没有任何进度条、百分比、步骤文字 |
| 要有音乐 | 素材带原声（AAC 160k），音量 0→0.85 渐入；收场 0.7 秒淡出 |
| 进出要有处理 | 进场：858ms 从黑淡入；出场：Opacity→0 + Scale→1.10（推近）共 700ms，然后主界面接管 |
| 可切换 / 可导入 / 只裁时长 | 设置 → 显示 → 启动入场动画：内置 3 段可选，也能「选择本地文件…」直接播原文件（**不转码、不掉画质**），并用「从第几秒播到第几秒」裁时长（0＝到片尾） |
| 取消首次全屏 | 去掉"首次启动强制全屏"；窗口位置/大小按上次关闭时的样子恢复（这套本来就已有） |

**踩到的两个真问题（都修了）**：
1. **WPF 画不过 HwndHost**（本项目早先量过的空域限制）：画面宿主是原生子窗口，永远盖在 WPF 内容之上。
   动画期间必须把各路宿主 `Collapsed`（`ApplyStageVisibility` 里加了 `_introActive/_introNative`），收场再恢复 ——
   否则遮罩会被画面子窗盖住，看到的是一片黑。
2. **`MediaOpened` 不保证触发**：实测有的时机它不触发，视频与标题就都停在透明状态 → 纯黑。
   WPF 回退路径里除了等事件，还加了 650ms 的兜底定时器（`_introKick`）直接起播。

**另一个如实说明（差点误判成"动画没渲染"）**：硬件视频层**用屏幕抓取（CopyFromScreen）会抓到黑**，
用 `PrintWindow(PW_RENDERFULLCONTENT)` 让窗口自己渲染就能拿到（实测亮部 50%、帧间变化 99%）。
所以"截图是黑的"不等于"用户看到的是黑的"。

**未验证**：原生入场窗口这一版**没有在真机上亲眼确认过**（用户要求我停止自己驱动界面验证）。
要看的点：① 点开图标后多久出画面；② 有没有声音、音画是否同步；③ 收场时主界面是否已就绪（不该再有加载等待）；
④ 设置里切换内置片段 / 导入自己的视频 / 裁时长是否都生效。

### 启动动画的编辑与预览（设置 → 显示） | 能力 | 说明 | | --- | --- | | 切换素材 | 3 个内置片段 + 「选择本地文件…」导入自己的（**原文件直出、不转码**） | | 改时长 | 「从第几秒播到第几秒」；**打开设置时读一次素材真实时长**（`Mp4Probe` 只读 `moov/mvhd`，不解码），结束秒默认就是整段时长，填超了自动纠回来 | | 再延长 | 「再延长 N 秒」：正片放完后**停在最后一帧**继续展示 N 秒；**这段里点一下/按一下就能跳过**（正片期间点击不响应，避免误触把开场切掉） | | 预览 | 「预览」按钮：立刻按当前设置播一遍，不用重启程序 | | 出场转场 | 白闪（90ms 升到 22% → 420ms 退掉）+ 画面明显推近（1.0→1.30，880ms）淡出 + 主窗口交叉溶解淡入 | 
### 悬浮提示不再遮挡画面
用户反馈："悬浮提示会遮挡内容，而且没有限制高度"。两处都改了：

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 状态浮层（右上角） | 明细单行不省略 → 会横向撑开；窗口没有 MaxHeight | `MaxWidth=360 / MaxHeight=300`，明细单行 + 省略号（`MaxWidth=300`）；**位置优先放进画面上方的黑边里**（黑边本来就没内容），黑边放不下才退回画面内右上角 |
| 提示条（右下角向上排队） | 正文只有 MaxWidth，没限高 → 一长条能盖到画面中间 | 正文 `MaxHeight=104` + 省略号，窗口 `MaxHeight=200`；**整摞总高封顶**（画面高度的 40%，最多 320px），同时最多 3 条，多余的旧提示条直接收掉 |

### 安卓鼠标控制：三个"先量再说"的决定
1. **adb 用随程序带的那一份**（`Assets\adb\`，来自 Google platform-tools，Apache-2.0，含 NOTICE）。
   查找顺序：自带 → PATH → `ANDROID_HOME`/SDK 常见位置。用户没装 Android SDK 也能用；
   界面上会写明当前用的是哪一份。
2. **`adb shell input tap` 用的是"当前方向"的显示坐标系** —— 这不是猜的，是量出来的
   （`tools/ui-spike/adb-verify.ps1` A 段，用「显示指针位置」在设备自己的帧缓冲上读回落点）：

   | 探针 | 结果 |
   | --- | --- |
   | 当前方向内的点 `(400,400)` | 落在 `(399.5,399.5)` |
   | **超出自然宽度**的点 `(2000,400)` | 落在 `(1999.5,399.5)`（自然宽度只有 1080，说明用的不是自然坐标） |
   | **超出当前高度**的点 `(400,2000)` | 被丢弃（这个点在自然方向里是合法的，却没有落点） |

3. **当前方向的尺寸要从 `dumpsys display` 读，不能拿 `wm size` 去推算**。
   实测（Android 14 模拟器执行 `wm size 2340x1080`）：`wm size` 报 2340×1080 而旋转仍是 0，
   若按"自然方向一定是竖屏"去 Min/Max 推算会得到 1080×2340，**坐标整体错位**。
   另外 `wm size` 的 **Override 优先于 Physical**（用户改过分辨率时生效的是 Override）。
   手机还会转，所以连着的时候每 4 秒重读一次尺寸/旋转，避免一直按旧尺寸换算。

4. **用户不需要填地址**（这一条是按用户反馈改的：投屏之后还要手填 IP 与端口，体验不对）。
   手机打开「无线调试」后会用 mDNS 广播 `_adb-tls-connect._tcp`（连接口）与 `_adb-tls-pairing._tcp`（配对 口），
   `adb mdns services` 就能列出来（本机实测可用，**不需要 Bonjour**；`adb auto-connect` 这条命令在 platform-tools 37 里并不存在，
   所以自动发现在程序里自己做）。程序的做法：
   - 打开「鼠标控制」开关 → 记过地址就先用；没记过（或连不上）就 `adb mdns services` → 逐个 `adb connect` → 连上即用；
   - 还没连上时每 10 秒自动再找一次（用户什么都不用做）；
   - 手机若跑过 `adb tcpip 5555`，会广播传统的 `_adb._tcp`，也一并试（覆盖 Android 10 的有线初始化路径）。

   **只有第一次**在一台新手机上需要配对码（Android 的安全要求，任何工具都绕不过）：
   手机点「使用配对码配对设备」→ 程序里填那 6 位（IP 与端口会自动填好）→ 以后就是"打开开关即连上"。

### 音频输出切换：Windows 没有公开的 setter
| 操作 | API |
| --- | --- |
| 读默认设备 | WinRT `MediaDevice.GetDefaultAudioRenderId()` ✅ 公开 |
| 写默认设备 | 只能走**未公开**的 `IPolicyConfig` COM 接口 |

必须两种 id 形式都试：WinRT 给的是**设备接口路径**（`\\?\SWD#MMDEVAPI#{...}#{接口GUID}`），而 `IPolicyConfig` 要的是 **IMMDevice 端点 id**（`{0.0.0.00000000}.{guid}`）。直接传前者会得到 `E_INVALIDARG`。

**验证纪律**：绝不拿"没抛异常"当成功。每一步都用 WinRT 读回校验。

### 设备识别：三个"不瞎猜"的硬决定
1. **苹果型号表刻意不完整**：公开标识符清单里 iPad Pro 的条目自相矛盾（同一代号被标成两代），**故意不收录** → 显示原始代码。
2. **安卓只推断到品牌**，且在界面标注为猜测、同时保留原始型号代码。
3. 什么都不知道就说「未知设备」。

数据来源：AirPlay 的 `deviceID`/`model`/`name`（SETUP 的 plist）与 `User-Agent`（请求头）——与 UxPlay 读的是同一批字段（`raop_handlers.h:756-759、816`）。
Miracast 侧 Windows **只给** `Transmitter.Name`/`MacAddress`，**没有型号与系统版本**（反射 SDK 确认），这是硬限制。

### 码率来源按协议区分，且含义不同
- **AirPlay**：实测吞吐（收到的字节 ÷ 实际经过时间）
- **Miracast**：平台协商值

图表刻意做成**两张独立小图**而不是一条双 Y 轴曲线——量纲不同，画在一起会误导。

| --- | --- | --- | --- |

| 9 | **没被聚焦的那一路断线后永远留在会话列表里** | 路数不归零、并发数显示错；两路都断了界面还显示有一路在投 | 做 ③ 时读 `OnSessionEnded` 发现只清理聚焦那一路（另一路子代理复核也独立指出） |
| 10 | **"HwndHost 会把鼠标事件回投给 WPF"是错的** | 小窗"拖画面挪窗"其实一直不生效（只在注释里写着能用）；⑧ 的鼠标控制也无从下手 | 逐层量：控件的 `WndProc` 收不到鼠标消息、控件的 WPF 鼠标事件 0 条、自装子窗口过程收到 60 条消息其中鼠标 **0 条**；**窗口级**事件才收得到 |
| 11 | 只按 `wm size` + 旋转推算屏幕尺寸 | 改过分辨率或横屏时坐标整体错位（2340×1080 会被算成 1080×2340） | 安卓 14 模拟器实测：`wm size` 2340×1080 而旋转为 0 |
| 13 | **所有设置都存不下来（用户报"开关关了下次又打开"）** | 用户改的每一个开关在重启后都会恢复默认 | 查 `%LocalAppData%\CastReceiver\settings.json` 的修改时间一直停在旧日期；`Load()` 每次都重写这个文件，说明写入被吞了。真凶：小窗位置字段 `MiniLeft/MiniTop` 的默认值是 `double.NaN`，而 `System.Text.Json` 默认**遇到 NaN 直接抛异常**，`Save()` 里又是空 `catch` → 静默失败 |
| 14 | **原生黑幕盖住了入场动画** | 用户看到"先一整屏黑、再主界面的转圈等待"，看不到视频 | 原来那块挡 WPF 启动的置顶黑幕被我改成了全屏，而且它在入场窗之后创建 → 盖住画面。现在：有入场动画时**不创建黑幕**；黑幕几何改成"上次关闭时的窗口矩形" |
| 15 | **双击图标完全没反应（程序启动就崩）** | 用户连点四五次都起不来 | `startup.log` 停在"开始创建原生黑幕"，stderr 里是 `NullReferenceException @ App.xaml.cs:210`：我把黑幕那段放到了 `Host = new CastAppHost()` **之前**，而它引用了 `Host.Settings`。改成轻量读一次配置，不碰 Host |
| 16 | **原生入场窗永不收场（一块置顶窗永远盖住界面）** | 用户看着像"点了没反应" | 两个原因：① 没订阅 `MediaPlayer.MediaEnded`，而"播到片尾"靠它置位；② 我给 `StartIntroIfEnabled` 打的"原生优先"补丁**根本没生效**（还是老的写死路径），于是从不去调用 `NativeIntroWindow.Finish()`。现在补上事件 + 位置/时长/秒表三重判据 + 停住 0.8 秒强制收场，实测 7.5 秒素材在 ~8.9 秒收场、之后只剩主窗口 |
| 17 | **`GetModuleHandle` 声明错了 DLL** | 原生入场动画直接起不来（日志：Unable to find an entry point in DLL 'user32.dll'） | 它是 `kernel32.dll` 的导出（`NativeSplash` 里原来是对的，我新写的文件抄错了） |
| 18 | **启动画面上下有黑边（用户以为是自己素材的问题）** | 入场画面被"上下补黑"，看着像宽银幕压扁 | 我给播放表面写了死的 `SetSurfaceSize(1920,1080)`（16:9），而素材是 2.53:1 → MediaPlayer 把画面**居中塞进 16:9 表面并上下补黑**，再被铺满窗体，黑边就"烤"进画面了。改成在 `MediaOpened` 里按 `NaturalVideoWidth/Height` 重建表面（照搬镜像链路里验证过的 `MatchSurfaceToVideo`）。日志会写"入场画面表面已对齐素材：1282×506" |
| 19 | **主窗口标题栏露在入场画面上面** | 入场画面之上还有一条"投屏Window"标题栏，像没盖住 | 入场窗用的是"设置里记的窗口矩形"，而主窗口实际显示的位置/尺寸可能不同（未恢复、最大化、DPI）。现在主窗口一显示就把入场窗**对齐到它真实的窗口外框**（`NativeIntroWindow.AlignTo`，走 `SetWindowPos`；并在移动/改变大小时持续对齐）。实测两者矩形完全一致：`200,150 1120x720` |
| 20 | **"再延长 N 秒"只延长了 1.18 秒** | 设 3 秒，实际不到 1.2 秒就被收场 | 进延长段要 `Pause()` 停在最后一帧，而 `PlaybackSession.PlaybackStateChanged` 里"看到 Paused 就当播完"的判断把**我们自己这次暂停**也算成了片尾。修法：`_inExtension` 守卫 + 先置标志再 Pause。日志留了"正片结束判据/进入延长段/延长段结束"三行，实测 3.0 秒 → 3.1 秒 |
| 21 | **补丁静默失败（我自己的工程问题）** | 代码"改了"但行为没变 | PowerShell 的 `-Raw` 内容是 CRLF，而我用 LF 的多行字符串去 `Replace` → 不匹配也不报错，于是"改了"其实没改（`GetWindowHandle` 守卫、日志插桩都中招过）。后来改用 edit 工具逐处改，才真正生效。**教训：多行补丁不要用 Replace，要用能报错的编辑方式** |
| 12 | 屏幕尺寸只在连接时读一次 | 手机转屏后"点哪儿都不对" | 实现每 4 秒重读；验证脚本里也加了护栏（实测遇到过尺寸被系统改回去） |

## 五、诚实清单（未验证 / 遗留）

1. **真实 iPhone 是否接受我们广播的 TXT/features 组合** —— 无设备，未验证。
   降低风险的事实：`0x527FFEE6`（第 27 位=0）是 UxPlay 默认值，是被大量真机使用的组合。
2. **合成视频在程序窗口里是否真的出画** —— ③ 这次补上了：并排截图里**主画面与格子都亲眼看到画面**
   （并且脚本按像素断言"不是黑屏"），这一条现在算已验证。
3. **③④ 只验证到 2 路**：两路同时投的真实流 + 18 项断言全过；3 路以上是按同一套逻辑外推的，
   **没有实测**（格子会自动等比缩小、排成右侧一列）。
4. **⑧ 的未验证部分（重要，别误读）**：
   - ✅ 已验证：随程序带的 adb 能被找到并连接、读屏幕尺寸/旋转、注入点击与滑动 ——
     在**安卓 14 模拟器**上端到端量过落点（误差 ≤3px），否定用例（黑边不点、关开关不点）也过。
   - ✅ 已验证（新增 C 段）：**"一个地址都不填、只打开开关"** → 程序自己发现并连上 → 鼠标点画面落在手机上
     （实测误差 0.5px）。做法是把 `adb mdns services` 的**真实格式**发现结果注入（`--adb-discovery`），
     连接与注入仍然真跑；另外自检里也有一条不带界面的同类用例（`--android-only --adb-endpoint <host:port>`）。
     之所以要注入：**模拟器广播的是它自己的 NAT 地址（10.0.2.15），宿主机连不上**。
   - ❌ **真机上的 mDNS 发现未实测**（没有真机）：真机广播的是局域网内可达的地址，逻辑与验证过的一致，
     但"真机能被发现"这一步只能靠真机确认。
   - ❌ **真机"配对码配对"（`adb pair`）未在真机上跑过**：模拟器没有可读的配对码界面。
     现在只做到"命令构造正确 + 成功/失败判定按 platform-tools 的输出文案"，并有状态机自检；
     真机配对这条路**必须实测过一次才算数**。
   - ❌ **真机横屏未实测**：本机模拟器拒绝真正旋转（`device_state_rotation_lock` 锁死）。
     所以"旋转后 input tap 用当前方向坐标"这条结论是用**改尺寸（2340×1080）** 的等价场景量出来的。
   - ❌ Android 10 及以下的"不支持无线配对"提示文案，没有在 Android 10 设备上实机验证。
5. **⑥ 缺设备选择界面**，目前只能改配置文件。
6. 本机跑**完整**自检会卡在 DLNA/媒体代理阶段（本机公网 TLS 不可用），
   且加密库组因 `%TEMP%` 写入受限报 Access denied —— 均为**既有环境问题**，与本次改动无关。
   所以验证走 `--airplay-only` / `--android-only`；README 里"45 项"的结论在这台机器上无法复现。
7. **`adb shell input` 的延迟**（⑧ 停用前的实测）：一次点击 = 起一个 adb 进程（真机无线上大约几十毫秒到上百毫秒），
   所以鼠标控制适合"点按/滚动"，不适合当触控板连续拖拽。拖动是"按下—抬起"一次性发一条 `input swipe`。
8. **入场动画的两点如实说明**：
   - 素材是**我挑的**（用户说"自由发挥"，并提供了 `C:\Users\Administrator\Desktop\MP4` 五个片段）：
     选的是 `26383288243-1-30120.mp4` 的 24.4→30.8 秒（舰队列阵环绕行星）。用户如果不喜欢，
     **换素材不用改代码**：把新的小片段覆盖 `assets\intro.mp4` 即可（规格：H.264 MP4、无音轨、约 1240×508）。
   - 动画总长约 **6.4 秒**；`--no-intro` 或设置里关掉都能跳过，启动时点一下也能立刻跳过。
     启动**没有变慢**的逻辑依据：动画跑在另一个线程、程序该干的活照旧并行进行；
     但如果用户觉得 6 秒太长，把 `Assets\intro.mp4` 换短一点即可（代码里的时长按 6.4 秒写，
     改素材后要顺手改 `MainWindow.StartIntroIfEnabled` 里的 `TimeSpan.FromSeconds(6.4)`）。
9. **启动入场动画：原生窗口先播这一版没有亲眼确认过**（用户要求停止自测）。要看的点见第二节该小节末尾的"未验证"。
10. **抽帧/裁片的工具链不随程序发布**：`tools\splash-tool`（MS 的 Media Foundation）+ 剪映自带的 ffmpeg。
   程序只带**成品** `assets\intro.mp4`（1.41MB）。
